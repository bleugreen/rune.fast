# rune.fast

The public record of an AI agent swarm that took a fresh account to 99 in all 19 skills on the 2004scape demo server in 35,787 logged-in ticks (3 h 58 min 34 s at 400 ms a tick), 129 ticks under the previous record of 35,916. The account reached #1 on 26 October 2026.

## Running it

```sh
bun install
bun run dev        # http://localhost:5173, including the /tokens design screen
bun run check      # typecheck, tests, production build, the public-identifier scan of dist/, and the first-load budget (needs Chrome)
```

`bun run build` writes the static site to `dist/`, each page with its own head and its content rendered into its HTML. The `/tokens` route renders the palette, type scale, figures, a sample chart, and footage in the shared frame (two 3D replays and a video clip); it exists only under `bun run dev`.

## How it is built

Vite, React 18 and TypeScript, with client-side routes from react-router and charts drawn as SVG from d3-scale, d3-array and d3-time. There is no UI kit and no CSS framework: every colour, face, size and space is a custom property in `src/styles/tokens.css`, and components style themselves with CSS modules.

The data lives in `data/` as the documenting agent exported it. `data/attempts-timeline.json` is checked in verbatim, including names the site must not publish. The build never ships that file as is: `vite.config.ts` replaces the import with the projection in `scripts/public-timeline.ts`, which keeps only the fields the pages render and redacts those identifiers, and `bun run check:public` fails the check if any of them reaches `dist/`: fleet helper and lab account names, private host names (the `rs-ashburn` and `bgsrv` machines, `.ts.net` and `.local` addresses), game-process tokens, home-directory paths, message id fields, the swarm's `cairn://` addresses (except the harness page's taught addresses, below) and IPv4 addresses. The data files keep those addresses as the project's traceability; every page prints a source as plain-words provenance instead (who, where, when in Pacific time), through the one address table in `src/lib/places.ts`. The timeline projection does this for each event's sources, `scripts/public-tricks.ts` for the tricks cards, both by way of `scripts/plain-source.ts`, which throws on any address or UTC time it cannot put in plain words. Every clock time on the site is Pacific on the 12-hour clock (`2:37 PM`, `4:14:43 AM` where seconds matter), and each page names the zone once, on the first clock time a reader meets: the route page's opening, the cost page's opening line, the first clip caption on the tricks page, and on the story page the draft's own dateline, so the story's figures and captions add none. Everything else prints the time bare. The formatters are in `src/lib/time.ts`, which builds the string from its parts because ICU versions differ on the space before the period. The data keeps UTC, and UTC never reaches a page except inside quoted words, which stay as they were said. `src/pages/clock.test.tsx` renders each route and fails on a second zone, or on a clock time in any other form. Place names are not host names: the story says the run host sat in Ashburn, Virginia, which is public (the demo runs in Fly's iad region). Rival players may be named for public leaderboard facts, their ranks and times, so the previous record holder appears on the story page; the timeline projection still drops the name along with the rest of the archival fields.

The cost page (`/cost`) reads the cost exports beside it: `summary.json`, `cost-data.json`, `roles.json` and `hourly.json` from the documenting agent's cost refresh, `billing.json` (the list-price table that refresh priced with, and the subscriptions the swarm ran on: six Claude Max plans by the end of the run and one ChatGPT Pro plan, $200 a month each), `swarm-events.json` (spawns, merges and messages per Pacific calendar day from the thread's event graph) and `swarm-activity.json` (agents producing output: distinct runs with at least one model-output event in each five-minute bucket, so warm idle sessions are not counted). Every dollar figure on that page is the list-price value of tokens, not money paid; the page says so once and compares it with the subscriptions, $1,400 a month prorated over the window by the average month, about $256. Days on the page are Pacific calendar days. `cost-data.json` also holds a turn-concurrency curve the page no longer draws, because warm idle sessions hold turns open and inflate it. `cost-data.json` and `roles.json` carry issue titles and unit names that name helper accounts and run hosts, so `scripts/public-cost.ts` projects them to the numeric fields the page draws, through the same Vite plugin as the timeline. `src/cost/model.ts` derives every figure the page writes, and `src/cost/model.test.ts` checks the exports against each other (the price table reproduces each model's and each Pacific day's cost from the hourly tokens), pins the page's claims, and fails if any number in the page's text is not one the model derived from the data.

The harness page (`/harness`) explains Cairn, the harness the run's agents worked in, to a reader who uses a coding agent but has never run a multi-agent harness, on the run's own objects: issue rs/843 from filing to merge, main's four-item write, the four minutes around rs/3's question to the operator, and the tenet ledger. Its data is `data/harness.json`, written on the operator's Mac by `uv run scripts/harness/extract.py <export.duckdb>` from the rs project's DuckDB export; `--verify` re-queries every source line's table and key and fails if one no longer resolves. Who filed an issue is defined once, in `scripts/issue_filer.py`, for every extractor that needs it, the home page's tree included: an issue is filed by its author (`issues.author_principal_json`, the agent whose write appended it), not by its parent, which is only where it reports and so where attention routes. The two differ for 238 of the issues filed before the #1; rs/843 was filed by rs/158's coordinator with `main` as its parent. The same module reads the moment of the #1 from `data/summary.json`'s `cut`. The harness page's Fig 2 and its section on threads count to that moment, as the tree does, while the page's head and its other figures cover the whole export, which runs on past it (rs/843 merged after the #1); `--verify` also recounts Fig 2's filings by author. The extractor keeps only what the figures draw, stores senders as plain ids (`rs/3 coordinator`), and refuses to write if any excerpt carries a forbidden identifier, an email address, or a cairn:// address outside `src/harness/addresses.ts`. Those ten addresses are the page's subject matter, so they are the one exemption to the public scan: `check:public` blanks exact, whole occurrences of them (`withoutAddresses` in `scripts/forbidden.ts`; a full stop after an address ends it, but a prefix of a longer address is not exempt) and still fails on any other, while the replay clip scan keeps the blanket rule. The build ships the file through `scripts/public-harness.ts`, which keeps only each source's plain words. `src/harness/model.ts` derives every figure and printed number; `src/harness/model.test.ts` reconciles the counts, pins rs/843's and rs/3's objects, tests the exemption against a fixture, and fails if a number on the page is not one the model holds. The page opens, before any diagram, on the operator's own screenshot of Cairn during the run (see Figures below), because a reader of a coding agent pictures one agent in one terminal. The image carries no date, so the extractor reads one off it (`screen_moment`): the elapsed time a pane shows on a call (rs/140's wait, 27 min 58 s in) gives the moment, 1:00:56 PM on Wednesday 21 October, and the write refuses unless every other anchor agrees: the calls the panes show come before it, the next ones they do not show come after, a second pane's elapsed time matches, the operator's half-typed message was sent later, and each pane's agent was at work then or its pull request open. Its caption is the page's first clock time, so it carries the zone. The page's two animations, rs/843's timeline and the rs/3 routing tree, run on one clock, `src/harness/player.ts`: they rest fully drawn, never autoplay or loop, pause when scrolled away, and travel only on Play or the Step button (`travelSpan`, tested in `player.test.ts`); the arrow keys and scrubbing snap, and under reduced motion nothing travels and a state change is a 120 ms opacity change.

The route page (`/route`) follows attempt 5 step by step on the hiscore's own clock, the logged-in ticks from 0 to 35,787. Its data is two files. `data/route-log.json` is the runner's record of the attempt from the swarm's post-run export (`bun scripts/import-route.ts <postrun-dir>`, run on the operator's Mac, which checks each file against the export's `MANIFEST.json`): every login session, the top-level step intervals inside them, every level-up the runner observed, and the account's hiscore page after the finish, whose 19 stamps are each skill's 99 as the tick it was reached. Error texts are dropped (they name helper accounts) and the importer refuses output that carries a forbidden identifier. `data/route-plan.json` is the run order's priced table as it stood when the attempt logged in (`bun scripts/import-route-plan.ts <rs-sdk checkout>`, read through `git show`, never from the fork's working tree): RUN-ORDER.md's last revision before the login, which the importer checks has the run commit's figures row for row; it keeps only the figures, plus the few ticks a row says it leaves to the scenario rows for the route as run (the body altar, the leather Crafting route, the knights' top-ups). Both ship through `scripts/public-route.ts`. `src/route/model.ts` lays the runner's sessions end to end with the short logins the runner never drove, which the timeline records (`SHORT_LOGINS` in `src/route/plan.ts`, each pointing at its event and the tick count its words give). Between two hiscore stamps the hiscore can count more ticks than those hold; that excess is drawn at the one login `UNASSIGNED_AT` names inside the bracket, hatched and labelled unassigned, since the stamps fix how many such ticks there are and not where. On that clock every 99 the runner logged lands on its stamp, which the model checks as it builds and `src/route/model.test.ts` pins, with the session tiling, the swarm's 35,225 and its 562 accounted for in named terms (`ledger`), the rail's levels, and each step's planned figure traced to its rows. The page prints none of that reconciliation: it ends on the record line, Agility 99 against the previous record, and the reconciliation shows only as the hatched stretches on the spine. `src/route/plan.ts` cuts the attempt into 8 stretches and 25 steps, each starting at a named interval of the step log; the words are `src/route/prose.ts`, functions of the model, and `src/route/route.test.tsx` fails on a digit typed into their static text (the game's own figures are `GAME_FACTS`, each with its source) and on any number on the page that is not one of its steps' figures, the finish's, or derived from them. The page maps scroll to the clock through `src/route/useReadingTick.ts`: each step section reports its points (its top is its first tick, each break line holds or advances the clock by its own ticks, its bottom is the next step's tick), and the reading line 40% down the window is interpolated through them, so the spine's 99 marks sit exactly where the rail turns a skill to 99. Nothing on it animates. At 64rem and wider the rail is a sticky column; below, a sticky strip whose ▾ opens the whole rail, and the gutter becomes a rule beside the text.

The story on `/` is the documenting agent's draft, placed verbatim. `data/story.md` is a byte-for-byte copy of it and `data/receipts/section-N.md` of its per-section dig files, both refreshed with `bun scripts/import-story.ts [path]`, which refuses a draft that no longer parses or no longer contains what the page anchors to it. `src/story/draft.ts` splits the draft into the title, the byline, six sections of paragraphs and quoted messages, and each section's sources; it never edits a character of the prose, and renders only two inline marks, `code` spans and *emphasis*. A section's sources are its key anchors from the draft's Receipts plus the source table of its dig file, and `src/story/sources.ts` puts them in plain words for the page (who, where, when, with addresses through the site's shared table in `src/lib/places.ts`): the files keep their cairn:// addresses, transcript turns and raw sequence numbers as the project's traceability, and the page prints none of them. The build and the tests load the draft through `scripts/story-module.ts`, so only the page copy and the plain sources reach the bundle and the draft's editorial header does not. What the page adds to each section (its anchor, dates, the one figure and the block it follows, the operator's short lines set again as margin quotes, the one outbound link) lives in `src/story/sections.ts`, and `src/story/story.test.tsx` renders the page and fails unless every paragraph of `data/story.md` is on it as a reader sees it (byte for byte, less the code and emphasis delimiters), the sources sit only inside the closed Sources disclosures and carry no cairn:// address, and every margin quote is the prose's own words.

The story opens on a hero beside its title: the whole run as a tree (`src/tree/RunTree.tsx`), from the main thread's creation at the top to the #1 at the foot, with y as exact time. Each issue is a branch growing from whoever filed it, its author (`issues.author_principal_json`, through `scripts/issue_filer.py`, the one definition /harness counts by too), not its parent link, which records where attention routed. The threads main created (`host`, `integration`, `markets`, `autoresearch`) grow from main like issues; `document`, which the operator opened, is a root of its own. Its data is `data/tree.json` and `data/tree-titles.json`, written on the operator's Mac by `uv run scripts/tree/extract.py <export.duckdb> --kinds <labels.jsonl>...`, which re-queries what it wrote (`--verify`: the counts, every issue number, every problem message's id and each thread's origin write). The red ticks are messages a language model read as reporting a problem: `scripts/tree/classify.ts` asks Cairn's decide endpoint one four-way question of each agent message's first 700 characters (`extract.py --texts` writes its input), resuming from the labels it already has, and the figure's Sources disclosure says the ticks are a model's reading. The build ships the drawing without its ids (`scripts/public-tree.ts`); the site ships no issue titles, so `data/tree-titles.json` is archival. `src/tree/model.ts` is pure (the units, their children and weights, and a layout per size), and `src/tree/model.test.ts` pins its counts to the export, every branch to a living parent, the thread attachments, the earliest-outermost placement that keeps later growth from crossing earlier, and the projections. The figure is static, one canvas drawn once per size and never on scroll, with its day and thread labels in HTML over it. From 64rem the title and byline stand to the tree's left (`.opening` in `src/pages/StoryPage.module.css`) and the tree keeps its natural tall shape, about one screen high and 0.85 times as wide, with the day labels on its right, away from the title; below 64rem the tree spans the column above the title, and on a phone it keeps its own narrower margins and thinner marks.

The timeline chart (`src/attempts/TimelineChart.tsx`) puts every attempt's logged-in time on one wall-clock axis; the story sets it three times, cropped to the hours of sections 4, 5 and 6. It draws each scored account's logged-in spans from a table in `src/attempts/model.ts`. Every span bound points at an event in the JSON, or at a clock time an event's text states, and the tests in `src/attempts/model.test.ts` fail if a bound no longer matches the data. Of the events it marks only deaths and the stops made while the account was in the world (`drawnMarks`); attempt 5's events in full are on `/route`.

The tricks page reads `data/tricks.json`, written by hand from the documenting agent's evidence inventory: one object per technique, with what the game normally does, what the run did instead, why the server allows it, the run steps in plain words, and at most one before-and-after saving. A saving records its basis (measured, inferred or estimated), and a technique the sources never measured has no saving, so its card claims none. Sources stay in the JSON with the swarm's addresses and appear only behind each card's closed `sources` disclosure, in plain words: the build replaces the file with `scripts/public-tricks.ts`'s projection, which prints `issue rs/47 (the wine route, merged)` for `cairn://p/rs/47 (…)`, names the rs-sdk fork for its paths, and turns UTC times into Pacific. Techniques the run weighed and left out stay in the file as the record (`kind: "rejected"`, one line each), and the page does not render them. `src/tricks/model.ts` groups the techniques, orders each group by the share of cost a measured trick removes, and counts the measured tricks that halve a cost for the page's subtitle; `src/tricks/model.test.ts` checks every chart has numeric figures and a basis, that no card text carries a bare run-step code, and the rulings on individual figures (the whole-run knife saving is inferred; Charge is published as its measured rate). A card names its clip by id, or carries frames (`stills`, below). A technique with nothing on screen to film has neither, and its card has no media cell: its chart moves into that column, and with no chart the card is its prose alone. A card may also carry `route`, an element id on the Route page and the words of the line under its prose that links there; the Route page gives each step its step id and each logged-out break `logged-out-N`, counting the run's breaks from one. `model.test.ts` checks that every card shows its clip, its frames or no media cell, that nothing on the page promises footage to come, and that every route link lands on an element the Route page renders.

## Clips

Every piece of footage on the site is registered in `data/clips.json`, the one answer to what footage exists, and drawn by the one `Clip` component in `src/clips/`. An entry is either a `video` (an MP4 in the world assets, see below) or a `replay` (a tick window of a published world-feed recording, drawn in 3D). Both carry a poster under `public/clips/` (a JPEG, and its AVIF beside it, which `bun scripts/world/posters.ts` encodes), a frame size, a length, a caption, the UTC instants of the first and last frame, the run step, and a source: `screen recording` (the run host's screen recording of attempt 5), `run feed` (the swarm's recording of the world feed, which is what a replay plays) or `lab film` (with the rs-sdk commit it was filmed from). The caption line prints what is on screen, then the recording time in Pacific through `clipWhen`, the step and the source. Both kinds share the frame: the poster with a single play mark at rest; on play, a hairline progress rule in the accent that can be dragged to scrub, and, for a lab clip, the server tick on screen from its trace (`clipTickAt`); a replay shows no counter, because its window is numbered in its recording's ticks (the feed's own, for the death recordings), which a reader would take for the run's scored count; click or Space plays and pauses, the arrows step a second, Home goes back to the start. It never autoplays, loops or plays sound, and returns to the poster at the end. Footage runs 10 to 15 seconds and a video stays under 3 MB; `src/clips/registry.test.ts` checks every entry against its files (the poster's size, a replay's length against its ticks at 400 ms, and, where `.world/` holds the video, its content, size, frame and length) and that every entry is placed on a page.

**Videos live in R2, not git** (tenet #2), like the replays and the cache. An entry's `src` is its key under the world assets, `clips/<id>.<sha8>.mp4`, the name carrying the content, so the object is served immutable; only its poster is under `public/clips/`. `scripts/world/publish-videos.ts` hashes a cut into `.world/clips/` (`--add <id> <cut.mp4>`, printing the entry's `src` and `bytes`), puts every registered video `.world/` holds onto the bucket (`--upload`, with the token loaded into that one process: `bun --env-file=<r2.env> ...`), checks what the bucket answers the site with (`--check`: 200, `video/mp4`, the size, immutable caching, CORP and CORS, and a 206 to a byte range, which a seek needs) and fills a fresh checkout's mirror from production (`--pull`). `--only <id,...>` narrows any of them to the named videos, so an upload puts exactly what was cleared for publication. Lab films are cut by `lab/films/deliver.ts` (see `lab/films/README.md`).

A moment too short for a clip, such as the tutorial skip, is shown as a strip of three or four frames instead (`stills` on its card in `data/tricks.json`, the images under `public/stills/`), captioned like a clip: images, not footage.

The 3D renderer draws the players and NPCs the world feed carries and the map from the game cache, and nothing else: no trades, interfaces, dialogs, the cannon, lit logs or other placed objects. A moment about those is a video. A replay's camera follows the account its recording follows and cannot be moved by the reader, so the frame needs no control of its own for it. Footage that fails says so in its frame: a video whose file errors, or a video or replay that makes no progress for 30 s after the reader plays it (`src/clips/watchdog.ts`), goes back to its poster with a message. Only the record account is ever named in the scene: a recording that follows another run account (attempt 4's death) follows it by its slot alias, and the overlay's `showFollowedName` option, which `src/replay/world.ts` turns off for a slot alias, leaves it unlabelled. Cuts from the screen recording follow RUNE tenet #4: cropped to the game canvas, never the window title, the OS login box, the tray or the SDK panel. The recording runs a constant 4 s behind the time in its file name (measured on the SDK log stamps and the tray clock on screen), so a frame's UTC is 25 Oct 06:42:26 plus its offset. `scripts/world/cut-recording.ts` holds every window cut since the finish clips, cuts them on the operator's Mac where the recording is, and hands each to `publish-videos --add`. Where the game's own login form is on screen (it shows the account name and the password's length in asterisks), a cut takes those frames out behind a dip to black, and the caption says the login form is cut out. On the tricks page a clip illustrates one technique only (`src/clips/registry.test.ts`); the story may place a clip a card also shows. The story places clips as figures in `src/story/sections.ts`, which lets a section carry more than one figure.

## Figures

A still too large for git, such as a full-screen screenshot, is registered in `data/figures.json` and lives in R2 beside the clips (tenet #2); small stills such as the hiscore board stay under `public/figures/`. An entry names its source image by SHA-256, the rectangles masked out of it (each with what it hides), its alt text, and its renditions: a column image about twice the widest the page draws it, as AVIF with a JPEG for browsers without AVIF, and the full size, every source pixel as lossless WebP, which for flat interface screenshots is both exact and smaller than lossy WebP. The page draws the column image and links it to the full size, where the text reads. `scripts/figures/publish-figures.ts` makes them on the operator's Mac (`--build <id> <source.png>`): it refuses a source whose hash or size differs, converts it to sRGB from its own profile, strips every piece of metadata, fills each mask with one flat grey (a visible block, not a blur, which a known font can sometimes undo), checks each mask is one colour in the masked image and in the lossless full size, and writes the renditions into `.world/figures/`, named by content (`figures/<id>.<width>.<sha8>.<ext>`), and their sizes into the entry. Nothing else in the image changes. `--upload`, `--check` (200, the type, size and dimensions, the content its name carries, immutable caching, CORP and CORS) and `--pull` work as `publish-videos` does. `src/figures/registry.test.ts` checks every entry, and where `.world/` holds a rendition, its content, size and dimensions.

## Replays

A replay is footage like any other: a `replay` entry in `data/clips.json`, placed where a page places clips, in the same frame. It names its recording (`replays/<recording>/` in the world assets) and its window in that recording's ticks, counted from the manifest's anchor; for the finish recording (26 October, 10:27 to 11:08 UTC: the recovery login at Lumbridge to Agility 99 on the Wilderness course) those are the scored session's own ticks, as the timeline numbers them. The engine is in its own lazily loaded chunk and nothing of it loads until a replay comes near the screen.

**One world per page** (`src/replay/world.ts`). Every replay embed on a page shares one worker pool, one loaded cache, one `MapViewer` (so map squares, textures and models stay warm from one embed to the next) and one WebGL canvas. They are made the first time a replay is played and kept for the page's lifetime. One embed holds the stage at a time: the one the reader last played. The canvas moves into its frame (moving a canvas keeps its GL context; `Renderer.suspend()` stops drawing between hosts without a teardown), the viewer starts a fresh live controller around the same world, and the embed it moved out of goes back to its poster. What each embed has of its own is its `ReplayDriver` (manifest, chunks, checkpoints, playhead); the last four are kept, so going back to one reuses what it fetched. A driver bound to a new controller restores a checkpoint on its next seek. The world opens at the window's first tick, held under the poster until the followed account is drawn on loaded ground with no map squares or entity bakes outstanding (or 3 s after the first frame), so the reader sees the window from its start. The same test, held for 0.8 s, sets the frame's `data-replay-ready` attribute that the screenshot and bench scripts wait on; a seek removes it the moment it starts. A load that makes no progress for 30 s before the scene is shown (no step of the claim, no cache bytes) puts the frame back on its poster with a message, and playing it again starts over; the console names the step it stopped at. A render worker that dies fails every call made to it from then on, so a dead worker surfaces as a load failure instead of a wait. `scripts/world/check-stage.ts` plays two embeds in turn in Chrome and fails if the page makes more than one live WebGL2 context or more than one pool's workers, or an embed is never drawn; it prints the JS heap at each switch.

**The engine** is `packages/world` (`@rune/world`), rs-dash's world renderer and live layer, which descend from dennisdev's rs-map-viewer through RS World; `packages/world/UPSTREAM.md` gives the lineage and what the port kept, dropped and changed, and `LICENSE` is its BSD-2-Clause licence. Both are published at `/licenses/` and linked from the footer. The package has its own tsconfig (strict, without the site's `noUncheckedIndexedAccess`, which upstream code was never written for) and the root typechecks it through a project reference with `tsc -b`. `packages/world/vite.ts` holds what the build needs: `.web.ts` modules ahead of their headless twins (so the browser decodes gzip with wasm), GLSL `#include` expansion, ES module workers, the licence files, and cross-origin isolation headers for dev and preview. `public/_headers` sets the same COOP and COEP site-wide on Pages, because the worker pool shares the cache through `SharedArrayBuffer` and a client-side navigation never re-fetches the document.

**Playback.** The live layer takes frames from a `FeedSource` and its cycles from a `WorldStepper`. On the live site that was a socket; here `ReplayDriver` (`src/replay`) is both. A frame received `recv` ms after its epoch's hello is applied at client cycle `floor((recv - helloRecv) / 20)`, before that cycle runs, through `FeedGate`, the socket client's acceptance rules as a pure function. The simulation has no clocks or randomness, so a clip played straight through and one restored from a checkpoint end in the same state; `packages/world/test/replay.test.ts` holds that at every tick of the fixture. The world only applies deltas, so seeking needs a full state to start from: `LiveWorld.snapshot()` and `restore()` carry it as JSON, with entities in Map order, because the order they are cycled in is itself state. Each chunk starts with a checkpoint, and the driver keeps one every 50 ticks while it plays. On an hour of the recording, a backward seek from the segment start took a median 6.5 s (p95 11.5 s); from the nearest 50-tick checkpoint, a median 9 ms (p95 90 ms) (`scripts/world/bench-seek.ts`).

**Loading.** The world starts its render workers first, so their module load and wasm init overlap the manifest and the 9.7 MB game cache; nothing is posted to a worker until the viewer hands it the cache. The cache comes through `src/replay/cache.ts`, one shared download that every caller joins, kept in Cache Storage by the engine. That download, and the engine's code with it, starts when a replay embed first comes within one viewport of the screen (an IntersectionObserver in `Clip`), unless the browser asks to save data. Map squares are queued by the first frame, after the camera is on the followed account. They load around the camera, so the follow camera always goes to the followed account: when a seek puts the account where no map square is loaded yet, the camera moves there at its last height until the ground under them arrives, rather than holding still (which would wait forever). `scripts/world/bench-ready.ts` loads each named embed cold `--runs` times, as `shoot.ts` drives it (optionally stepping with the arrow keys), and reports the distribution of time to ready; under `bun run dev` it prints `window.__replay()` (the claim's step, the driver's seek state, the follow and the renderer's outstanding work) for any load that misses. Under the dev server, Vite reloads the page when a watched file changes, and on macOS the event for a file written just before the server started can arrive seconds later, so after editing `data/clips.json` wait a few seconds before shooting; both scripts fail a shot at once, saying so, if the page reloads. `scripts/world/bench-load.ts` scrolls an embed near, then into view, plays it, and gives the median load stages from the page's User Timing marks, alternating runs with and without the near-view start.

**Publishing a clip** runs on the operator's Mac, where the recordings and the cache are:

```sh
bun scripts/world/sync-local.ts <rs-dash>/caches     # the cache store into .world/cache/
RUNE_SCORED_ACCOUNT=<record account> [RUNE_FOLLOW_ACCOUNT=<attempt account>] \
  bun scripts/world/publish-clip.ts --clip <id> --recordings <recorder>/out [--upload] [--upload-cache]
bun scripts/world/shoot.ts --base http://localhost:5173 --page /tokens \
  --shot agility-lap@0:agility-lap --bare --scale 2.5   # a still through the frame's controls; a poster with --bare
```

Every clip is a row of `scripts/world/clips.ts`: its UTC window, the account its camera follows and that account's measured roster slot, how its ticks are numbered, the timeline marks the numbering must hit, and for a death the beats the window must hold. The clips are `finish` (26 Oct, 10:27 to 11:08 UTC, the final recovery through Agility 99), `spider-death` (26 Oct, 03:40:23.5 to 03:40:38.5 UTC: the record account's abandoned body among the poison spiders, its last hit splats, the death and the Lumbridge respawn) and `attempt-4-death` (24 Oct, 14:23:18 to 14:23:33 UTC: attempt 4's account poisoned at the Grand Tree door, the death and the respawn). The death clips number ticks as the feed does (`kOffset` 0), and the publisher fails unless the followed slot reaches 0 HP and is then first seen on the respawn tile inside the window. `publish-clip` chains the recorder's hourly files from the last hello before the window, gates every frame, redacts it, simulates headless with the real cache loaders up to the window, and writes one-minute chunks, each led by its checkpoint, brotli-compressed and named by content hash, plus `manifest.json` (chunk table, the timeline anchor, the account's out-of-view stretches) into `.world/replays/<clip>/`. The manifest's chunk table is the seek index: byte offsets would not be addressable inside brotli-encoded objects. It checks each clip's marks within 100 ms of the timeline's time: Agility 99 on session tick 6095, and attempt 4's respawn jump on feed tick 216740. `.world/` is gitignored and never under `public/`; dev and preview serve it at `/world-assets/`, as the bucket serves `world/`.

**Redaction** (`scripts/world/redact.ts`) happens to every frame before it is simulated, so checkpoints inherit it. The scored account's name comes only from the environment, and the script fails closed without it, or if the followed account holds no roster slot, more than one, or another slot than the clip's in the window. A clip may follow an account other than the record one (attempt 4's): its name comes only from `RUNE_FOLLOW_ACCOUNT`, it is redacted like every other player and added to the scan's names before the first frame, and the manifest follows it by its slot alias (`slot_994`), so that clip names no one; the redactor refuses a followed account that is the record account under any spelling. The clip id is published too and scanned with everything else, so a clip id must not contain a word that is some player's account name in its chain (the scan rejected attempt 4's first id that way). Every other player's name, in rosters and inside appearance blocks, becomes its slot (`slot_1167`, shown as Slot 1167); players' chat and overhead text are dropped; NPC text that names any player is dropped. Before anything is written for upload, the script scans every byte it wrote, by whole words and blind to case and separators, for every name it saw, decodes every appearance block, and applies the same forbidden-identifier list as `check:public` (`scripts/forbidden.ts`); one hit deletes the output. Its report carries counts and slots, never names. For the finish clip it replaced 8,377,034 roster names and 24,882 appearance names, dropped 148 player texts, scanned for 1,700 names and found none. `scripts/world/redact.test.ts` holds the same property on the fixture, whose names are all fictional.

**Hosting.** Production reads `VITE_WORLD_ASSET_BASE` from `.env.production`: the R2 bucket `rune-fast-assets` behind `assets.mage.md`.

## Fonts

Self-hosted from `src/fonts/`, which the CSS and `src/lib/fonts.ts` import, so the build names each file by its content under `/assets/` and it can be cached for good (see Deploying). Both are under the SIL Open Font License 1.1; the licences and `FONTLOG.txt` are served from `public/fonts/`.

- **Rune Serif**, a Latin subset of Source Serif 4 (Adobe, variable weight and optical size). The licence reserves the name "Source" for unmodified fonts, so the subset carries its own name. `src/fonts/full/` holds that subset with every OpenType feature; `uv run scripts/fonts/subset.py` writes the files served, which keep every character and both axes but only the layout features in `src/fonts/subset.json`, the defaults and the four figure styles the CSS asks for (roman 196 KB to 129 KB, italic 167 KB to 139 KB). `src/fonts/subset.test.ts` fails if the CSS turns on a feature the served files lack, or a face lacks `font-display: swap`.
- **IBM Plex Sans**, IBM's own unmodified Latin1 files at weights 400, 500 and 600.

## Titles and link previews

A link unfurler (Discord, X, iMessage, Slack, LinkedIn) runs no JavaScript, so each page's title, description and preview tags must be in the HTML Pages serves for it. `src/meta.ts` is the one source: each page's title (the story's own title for `/`, `Route · rune.fast` and so on for the rest) and its one-sentence description, whose figures come from the same data and models the pages print (the record's play time, the cost page's list value and subscriptions). In the browser, the Layout sets the document's title and description from it on every navigation. After `vite build`, `scripts/page-heads.ts` writes each page's HTML: the built shell with the page's head at the `<!--page-head-->` marker in `index.html` (title, description, author, canonical URL, Open Graph and X card tags, every URL absolute on https://rune.fast but the story's `article:author`, the operator's site, which only the article type defines). The same `AUTHOR`, in `src/lib/site.ts` so the entry need not load `src/meta.ts`, is the footer's 'Operated by' byline, on every page and both error pages. It writes `dist/index.html` for `/` and `route.html`, `tricks.html`, `cost.html` and `harness.html` beside it, because Pages serves `route.html` at `/route` and redirects `/route/` and `/route.html` there (and `/index.html` to `/`), whereas it serves a `route/index.html` only at `/route/`, redirecting `/route` to it. Every page file is the same app beneath its head, with the page rendered into its root (see First load); `dist/404.html` is the Nothing here page's, titled and marked `noindex`, which Pages serves for every other path. `src/meta.test.ts` checks the module and each page's head, `check:public` checks the files the build wrote, and `bun run check:heads`, run against `wrangler pages dev dist`, opens each page in Chrome and checks what it serves, that it renders, and that its nav routes client-side with each page's title.

Every page shares one preview image, `public/share.png` (1200 by 630): the story's opening, with the site name, the title and the run as a tree on paper. It is drawn from the dev-only `/share` screen (`src/dev/Share.tsx`) by `bun run render:share` with `bun run dev` running, which also draws the favicon's PNGs from `public/favicon.svg` (Rune Serif's r in ink on paper): `favicon-32.png` and the 180 px `apple-touch-icon.png`. Like the site's other figures, all of them are checked in.

## First load

Most readers land on the story page, some over slow links (the record's first report was a 55 s load; a reader in Perth is served from Frankfurt, 250 to 300 ms away), so its first load fetches what its first screen needs and nothing more: the shell, the story's text and the tree. `bun run check:load` holds that, in `bun run check`.

- **Each page is in its HTML.** The build renders every page into its own HTML file, so the masthead, the page's text, its figures' reserved frames and the footer paint as soon as the HTML, the stylesheet and the roman serif are in, without waiting for any script; the app then hydrates the page in place. It is one app with one route table (`src/routes.tsx`): `vite.config.ts` builds a server entry (`src/server.tsx`, into `dist-server/`, never deployed) in the same run as the client and through the same plugins and defines, so it renders the data's public projections, the same CSS module class names and the same build date, and `scripts/page-heads.ts` renders each page with React's server renderer inside React Router's static handler, which resolves the lazy page routes, and writes it into the page's root, marked `data-prerendered` with the page it is. In the browser, `src/main.tsx` loads the landing page's own chunk before the first render, then hydrates the root if it was rendered for this path and renders from scratch otherwise (the dev server, whose shell is empty). Nothing in a first render may read the browser: the window, `matchMedia`, the location outside the router, or a measured size. What depends on them starts from the value the server draws and changes in an effect, as the charts' widths (a fallback width, then the measured one), reduced motion and the run tree do; the tree's frame, caption and sources are in the HTML, and its canvas and the labels laid out over it are drawn once its data is in and its size measured. Every date and number is formatted in a fixed locale and the Pacific zone (`src/lib/time.ts`, `src/lib/numbers.ts`), so a reader anywhere renders the build's text. `bun run check:prerender` checks that each built page carries its own h1 and first paragraph as the components render them from the data, that every page reads with JavaScript off, and, in a copy of the build with React's development build, that every page and an unknown path hydrate with nothing logged and keep the server's DOM.
- **The entry** is the shell, the story page and its text. Every other page is a chunk of its own with its data, which the router loads when it is visited. `src/meta.ts`, which works every page's description out of the data and models, is loaded by the Layout only to retitle a client-side navigation, since the landing page's head is already in its HTML; what the entry needs of the site's facts is in `src/lib/site.ts`. The budgets are 150 KB of initial JavaScript, brotli-compressed, and 180 KB for the story page's HTML (about 22 KB, since it carries the story, which the entry also holds to hydrate from) and that JavaScript together.
- **Each page's HTML preloads what its first screen needs beyond the entry**: the story page the tree's data, the site's largest (`data/tree.json`, a chunk of its own, `src/tree/data.ts`), so the hero, whose height is reserved, draws when it lands; every other page its own chunk, the chunks it imports and their stylesheets, so the page is styled from its first paint and its chunk downloads beside the entry; Nothing here its own small chunk. The build writes these into the shell marked `data-page` with their page (`PAGE_CHUNKS` in `vite.config.ts`) and `withHead` keeps each in its page's HTML alone.
- **Rune Serif's italic** is registered from script (`src/lib/fonts.ts`), because a face in CSS is fetched as soon as any text in the document needs it. The story page's first screen sets no italic and its prose below has plenty, so it registers the italic once the tree is drawn and the page has loaded; every other page registers it at once.
- **Clip posters** load lazily, decode off the main thread, and come as AVIF with the JPEG as fallback. A video element carries no poster of its own: browsers fetch a poster attribute at once, wherever the clip is on the page.
- **Cloudflare Web Analytics** is added by the app after the load event, when the main thread is idle, and only on rune.fast (`src/lib/analytics.ts`). Cloudflare's own injection must not reach the HTML: the rune.fast zone (free plan, where RUM is on by default) adds a module script to every HTML response it may transform, which holds DOMContentLoaded until it arrives, or until a network that drops its host gives up on it, and loads the beacon a second time. The pages' HTML is therefore served with `Cache-Control: no-transform` (see Deploying).

`scripts/check-load.ts` fails on more initial JavaScript, or HTML and JavaScript, than the budgets, and on any request the story page makes without scrolling, on a desktop and a phone, that its first screen does not need: only the document, hashed files under `/assets/`, the roman serif, the sans and the favicon, then the italic after the tree is drawn and the page has loaded, and the analytics beacon after load. Chrome resolves rune.fast to `vite preview` so the page runs as on the site, and the beacon is answered with an empty script, so nothing is sent. `--measure` prints first contentful paint, the frame that first holds the title, largest contentful paint, DOMContentLoaded, load, when the tree is drawn, and bytes and requests, plain and on emulated 1.6 Mbps links at 300 ms and 600 ms round trip, then the paints of every other page on both slow links.

## Deploying

Cloudflare Pages builds the site from `main`. The project is configured in the Cloudflare dashboard, not in this repository, so there is no `wrangler.toml`:

- Build command: `bun run build`
- Build output directory: `dist`
- The build emits a top-level `404.html`, so Pages serves it, with status 404, for any path that is neither a file nor a page (`/attempts`, the removed page, among them), and the app hydrates it as the 'Nothing here' page. Without it Pages would treat the site as a single-page app and serve `index.html`, now the story's own HTML, for every unknown path. Each page has its own HTML file (see Titles and link previews), so `/route` and the rest are served their own head and content, and the client router takes over from there. `bun run check:heads` against `wrangler pages dev dist` checks each page's addresses, the 404s, and client-side navigation between the pages.
- The root directory is the repository root, so Pages also builds the Function in `functions/`.
- Caching: everything under `/assets/` is named by its content, so `public/_headers` lets browsers keep it a year without asking again (`immutable`); the pages' HTML keeps Pages' `max-age=0, must-revalidate`, so a deploy shows at once, with `no-transform` added; and unhashed files (posters, figures, icons, licences) keep Pages' default. Nothing whose name does not change with its content may be marked immutable. Pages applies every `_headers` rule that matches, in file order, each rule's `! Name` detaches before its sets, and a header set twice is joined with a comma. So the HTML's Cache-Control sits on `/*`, the only pattern that reaches every page, and each other rule detaches it before setting its own. A path written twice keeps only its later block. `scripts/pages.test.ts` models that and pins the result for pages, assets and every top-level entry of `public/`; `check:heads` checks what `wrangler pages dev` actually serves for every file of the build.
- Web Analytics: the app adds the beacon itself (see First load). Its token is the rune.fast zone's own Web Analytics site, the free plan's automatic setup, which takes reports only at the zone's same-origin `/cdn-cgi/rum`: the manual-install endpoint, `cloudflareinsights.com/cdn-cgi/rum`, answers 404 for it. So the beacon's config sends there (`send.to`), and the zone's RUM must stay on. Its automatic injection is kept out of the HTML by `no-transform`, not by a dashboard switch (the current dashboard has none for it). The Function adds `no-transform` to any HTML it serves, because `_headers` never reaches a Function's response. `404.html` is not covered: after applying `_headers`, Pages replaces a 404's Cache-Control with `no-store`, so the zone still injects its beacon into the Nothing here page, which therefore loads it twice. After a deploy, `bun run check:live` fetches every page and an unknown path on rune.fast and www.rune.fast and fails on HTML without `no-transform` or with any beacon reference (so, for now, on the 404), then opens each home page in Chrome and requires exactly one beacon script, ours, and a 2xx answer from the zone's `/cdn-cgi/rum`. Each run records one real page view per host.

**Surviving a deploy.** Pages serves only the current deployment's files, so a tab opened before a deploy asks for chunks, workers and stylesheets by hashed names that no longer exist. Left to Pages, such a request gets an HTML page (the app shell before `404.html` was emitted, now `404.html`), and the browser fails to run HTML as a module. Three parts handle this:

- **Missing files are 404s.** `functions/[[path]].ts` turns Pages' HTML answer for a path that names a file into a plain-text 404, and sets COOP and COEP itself, because Pages applies `_headers` only to static responses. The build writes `dist/_routes.json` (`scripts/pages-routes.ts`), which routes only the build-output directories (`assets/`, `fonts/`, `licenses/`, `clips/`) to the Function and excludes every file the deploy has. Real files are therefore served statically and free, and only misses run the Function. `check:public` fails if `_routes.json` does not match the build.
- **A stale tab reloads once.** `src/lib/deploy.ts` reloads the page when a chunk fails to load: through Vite's `vite:preloadError` event (`src/main.tsx`), through the routes' error element, and, before the replay starts its workers, when the entry module named by the served `index.html` differs from the one the tab is running. A module worker that fails to load would otherwise leave the replay waiting. A timestamp in `sessionStorage` stops a second automatic reload within a minute, so a genuinely broken asset ends on the error page instead of looping.
- **The error page is the site's.** `src/pages/LoadFailed.tsx` is the `errorElement` for every route, inside the layout, in place of React Router's developer screen: one sentence, a Reload link and a link back to the story. A render error inside a replay stays in the replay's frame (`src/components/Contained.tsx`).
